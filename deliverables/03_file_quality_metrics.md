# File quality metrics (deliverable 3)

The metrics used to grade the price transparency (PTD) files, how each is calculated, and why, with the score of every file we use. Generated by `pipeline/c3_report.py` from the C3 outputs; the full reasoning and decision history are in `LOGIC.md` section 3C.

## 1. What is graded

- **Every Centene file:** the 4 index files (tables of contents) and the 33 rate files they link: Ambetter 28, Health Net 2, Fidelis 2, QualChoice 1. Our in-scope file (Health Net CA, commercial group PPO) is one of them; the rest show the metrics work on any payer's file.
- **Against what:** 45 CFR §147.212 as in force on 1 Oct 2025 (the October 2026 rule keeps it until 6 Mar 2027), the CMS JSON schema at the version each file declares (v2.0.0; Ambetter OH v1.0.0), and data-quality checks against CMS reference data (2026 Medicare fee schedule, HCPCS, place-of-service codes, NPPES, Doctors and Clinicians) and the HiLabs code weights.

## 2. How the scores are built

| Step | Calculation | Why |
|---|---|---|
| Metric score | Each metric gives numerator, denominator, value and a score from 0 to 1 (higher is better); "share of bad" metrics score 1 − share. | One scale for every metric; raw counts stay visible. |
| Gate | Reachable (M1, I1): 1 or 0, multiplies the file or index score. | A file nobody can download has no usable data. |
| Group score | Plain average of the group's measured metrics. | Multiplying would let one weak metric wipe out a group; averaging gives partial credit and is easy to explain. |
| Rate-file score | Gate × weighted average of groups: Timeliness 10%, Compliance 45%, Plausibility 25%, Usability 20%. | Compliance (what the rule and schema require) weighs most; then plausibility, because wrong values mislead negotiators. |
| Index score | Gate × weighted average of groups: Timeliness 10%, Compliance 45%, Consistency 15%, Usability 30%. | An index holds no prices, so plausibility is replaced by consistency with the files it links. |
| Unmeasurable metrics | Left out, weights re-normalized over what was measured; listed with the reason. | Scoring them 0 would punish the file for our missing reference data; 1 would reward it. |
| Requirements vs guidance | Compliance holds only what the rule or schema enforces; CMS README guidance sits in usability, marked (guide). | A file is not called non-compliant for breaking an unenforced convention. |
| Dataset score | index score^0.3 × (mean rate-file score)^0.7; an unreachable rate file counts 0. | Index and rate files are links in one chain, so their qualities multiply and a zero in either gives 0; the exponents give the rate files (where the prices are) more influence and keep the 0–1 scale. |

## 3. Rate-file metrics

| # | Metric | Group | How it is calculated | Why | Basis |
|---|---|---|---|---|---|
| M1 | Reachable | Gate | GET on the URL the index lists. HTTP 200 or 206 scores 1, anything else 0. Multiplies the file score. | A file nobody can download has no usable data, whatever else is true of it; the rule requires public access. | 45 CFR §147.212 (Oct 2025) (b)(3) |
| M2 | Freshness | Timeliness | d = run date − `last_updated_on`. 1 if d ≤ 31, else e^(−(d−31)/10). | The rule requires monthly updates. After the cycle the score falls fast (a week late 0.50, a month late 0.05) but never reaches 0, so very old files stay comparable. | 45 CFR §147.212 (Oct 2025) (b)(4) |
| M3 | Index-to-file lag | Timeliness | L = index `last_updated_on` − file `last_updated_on` (≤ 0 when the file is newer). Same curve as M2. | An index much newer than its files describes plans whose rates may have changed (staleness). | Quality |
| M4 | Contract currency | Timeliness | Prices with a valid `expiration_date` on or after the run date ÷ prices. | Expired rates are no longer payable (staleness). The share of `9999-12-31` (no end date) is reported. | 45 CFR §147.212 (Oct 2025) (b)(1)(i)(C)(2) |
| M5 | Required fields | Compliance | Objects with every required field present, non-empty and correctly typed ÷ objects, averaged over object types (header, provider references, providers, TINs, items, rates, prices), per the schema version the file declares. | Missing fields mean prices or providers cannot be read. Averaging over object types keeps a broken header from being drowned out by millions of prices. | CMS schema (declared version) |
| M6 | Valid enumerations | Compliance | Values in the allowed set ÷ values checked (`negotiation_arrangement`, `billing_code_type`, `negotiated_type`, `billing_class`, `setting`, `tin.type`). | Unknown values cannot be interpreted. | CMS schema |
| M7 | Conditional requirements | Compliance | Objects meeting the condition ÷ objects it applies to: `service_code` on professional prices; `business_name` on EIN TINs; `plan_sponsor_name` on EIN plans. | Without a place of service a professional rate cannot be matched to a setting. | CMS schema |
| M8 | Reference integrity | Compliance | Provider reference IDs used by prices that resolve to a provider group ÷ IDs used. | A price that points to no provider cannot be used. | CMS schema |
| M9 | Valid billing codes | Compliance | Items whose code fits its type (CPT 5 digits or 4 + F/T/U/M; HCPCS Level II on the CMS list, or CPT form; RC 4 digits; MS-DRG 3 digits; HIPPS 5; NDC 11) and have a description ÷ items. | Malformed codes (revenue codes without leading zeros) break every join on the code: Medicare comparison, coverage and cross-payer benchmarks. | 45 CFR §147.212 (Oct 2025) (b)(1)(i)(B) |
| M10 | Valid NPIs | Compliance | NPIs that are 10 digits, start with 1 or 2 and pass the CMS Luhn check digit (constant 24) ÷ NPI entries; `0` (TIN-level contracts, allowed by the schema) is counted separately. | An invalid NPI cannot be linked to a provider, address or specialty. | 45 CFR §147.212 (Oct 2025) (b)(1)(i)(C); CMS NPI spec |
| M11 | Valid TINs | Compliance | TINs that are 9-digit EINs with an IRS-issued prefix (or a valid NPI when `tin.type = npi`) ÷ TIN entries. | Invalid TINs break provider grouping; prefixes the IRS never issued, on individual clinicians, are consistent with SSNs, which the schema says to replace with the NPI. | 45 CFR §147.212 (Oct 2025) (b)(1)(i)(C); IRS EIN prefixes |
| M12 | Valid place of service | Compliance | Place-of-service codes on the CMS list, or `CSTM-00`, ÷ codes. | An unknown setting makes the rate ambiguous. | 45 CFR §147.212 (Oct 2025) (b)(1)(i)(C) |
| M13 | Dollar rate types | Compliance | Prices typed `negotiated`, `fee schedule`, `derived` or `per diem` ÷ prices (rate types). | The rule requires dollar amounts unless none can be set in advance; percentages of charges cannot be compared. | 45 CFR §147.212 (Oct 2025) (b)(1)(i)(C)(1) |
| M14 | \$0 / negative rates | Plausibility | 1 − prices with `negotiated_rate` ≤ 0 ÷ prices. | \$0 or negative rates are placeholders, not prices; the schema requires a rate above 0. | CMS schema; Quality |
| M15 | Outliers vs Medicare | Plausibility | For professional CPT/HCPCS dollar prices with a 2026 Medicare fee (code, modifier, the file's state, facility or non-facility by place of service): x = ln(rate ÷ Medicare), pooled over the file. Score = 1 − share outside Q1 − 1.5·IQR … Q3 + 1.5·IQR; beyond 3.0·IQR reported as extreme. | Rates far from the file's usual ratio to Medicare are likely errors. Log scale because rates scale multiplicatively (skewness 1.13 raw, −0.16 log); IQR fences are data-driven rather than a fixed multiplier. Pooling via the ratio covers codes with few prices. | Quality; CMS PFS RVU26D |
| M16 | Internal outliers | Plausibility | Per price key with at least 10 deduplicated prices: x = ln(rate). Score = 1 − share outside the same IQR fences. | Catches data-entry and unit errors among prices for the same service. | Quality |
| M17 | Provider validity | Plausibility | Distinct NPIs found in NPPES and not deactivated (main file + monthly deactivation report) ÷ distinct NPIs. | Rates for providers who can no longer bill are stale (provider validity). | Quality |
| M18 | Entity type vs billing class | Plausibility | 1 − institutional prices on groups listing only individual (Type 1) NPIs ÷ institutional prices. | Facility fees are paid to organizations; an individual-only list is likely wrong. | Quality |
| M19 | Duplicate rows | Usability | 1 − (raw price rows − distinct group × service × rate rows) ÷ raw price rows. | Duplicates inflate the file and every count taken from it (Health Net CA: 1.5 million rows, 39,960 distinct). | Quality |
| M20 | Repeated items | Usability | 1 − billing codes appearing in two or more items ÷ distinct codes. | Repeated items are the source of most duplicates and make it unclear which item is real. | Quality |
| M21 | Code coverage | Usability | Σ weight of the 583 HiLabs codes priced in the file (billing code or revenue-code sub-code) ÷ Σ weight of all 583; weight = sum of SPEC_PROC_WEIGHT over specialties. | Code coverage weighted by what the business uses most: missing high-volume codes hurt negotiators most. | Quality; HiLabs weights |
| M22 | Provider coverage (reported) | Reported only | Active in-state NPIs with a HiLabs-specialty taxonomy in the file ÷ the same count in NPPES. **Reported, not scored.** | Provider coverage measures how broad a network is, not whether the file is right: a narrow network published perfectly scores low (0.0003–0.37 here), so scoring it would penalize network design, not file quality. | Quality |
| M23 | Network named | Usability | Provider groups with a non-empty `network_name` ÷ groups. | Without network names a file that mixes networks cannot be split by network (why C2b had to infer PPO rates). From March 2027 the rule requires one file per network. | Quality; schema allows `[]` |
| M24 | Unexplained rate conflicts | Usability | 1 − provider (TIN + NPI) × service keys priced at different rates in groups whose `network_name` does not tell them apart ÷ keys priced in two or more groups. | Different rates can be legitimate across networks, so only conflicts the file gives no way to resolve count. A negotiator cannot tell which rate applies. | Quality |
| M25 | File naming (guide) | Usability | File name matches the CMS pattern. **Not measurable here.** | The CMS naming standard covers single-plan files only; files listed in an index have none, which every Centene rate file is. | CMS guide |
| M26 | Bundle and capitation code lists (guide) | Usability | `bundle` items with `bundled_codes` and `capitation` items with `covered_services` ÷ such items. | A bundle or capitation price is meaningless without the services it covers. | CMS guide (not enforced) |
| M27 | Percentage format (guide) | Usability | Percentage prices given as whole percentages (1 < value ≤ 100) ÷ percentage prices. | A value of 1.0 could mean 100% or 1%. | CMS guide (not enforced) |

## 4. Index-file metrics

| # | Metric | Group | How it is calculated | Why | Basis |
|---|---|---|---|---|---|
| I1 | Reachable | Gate | GET on the index URL; HTTP 200 or 206 scores 1, else 0. Multiplies the index score. | An index nobody can download makes every file it lists unfindable. | 45 CFR §147.212 (Oct 2025) (b)(3) |
| I2 | Freshness | Timeliness | Same curve as M2 on the index's `last_updated_on`. | Staleness of the plan list and links. | 45 CFR §147.212 (Oct 2025) (b)(4) |
| I3 | Required fields | Compliance | Required fields present and valid, averaged over object types (root, reporting structures, plans, file locations). | Missing fields leave plans or links unreadable. | CMS table-of-contents schema |
| I4 | Valid enumerations | Compliance | `plan_id_type` ∈ {ein, hios} and `plan_market_type` ∈ {group, individual} ÷ values. | Plans must be classifiable. | CMS schema |
| I5 | Conditional requirements | Compliance | `plan_sponsor_name` on EIN plans; each reporting structure links an in-network or allowed-amount file. | Sponsor and files must be identifiable. | CMS schema |
| I6 | Plan ID matches its type | Compliance | Plan IDs matching their declared type (EIN: 9 digits with an IRS prefix; HIOS: 5 digits, or a 10/14-character ID with a valid state code) ÷ plans. | Mislabelled IDs (HIOS IDs typed `ein`) break joins with CMS plan data and state detection. | CMS schema; 45 CFR §147.212 (Oct 2025) (b)(1)(i)(A) |
| I7 | Plan ID at the required level | Compliance | Plan IDs at a level the rule allows (14-character HIOS plan ID, 5-digit HIOS issuer ID, or EIN) ÷ plans; 10-character HIOS product IDs fail. | A product ID covers many plans, so the index cannot say which plan a file serves; CMS lists 14-character plan IDs for 51 of Ambetter's 119 products. | 45 CFR §147.212 (Oct 2025) (b)(1)(i)(A) |
| I8 | Out-of-network file linked | Compliance | Reporting structures linking an allowed-amount (out-of-network) file ÷ structures. | The rule requires the out-of-network file. | 45 CFR §147.212 (Oct 2025) (b)(1)(ii) |
| I9 | Linked rate files reachable | Consistency | Distinct linked in-network URLs answering HTTP 200/206 ÷ links. | A dead link leaves its plans with no published rates. | 45 CFR §147.212 (Oct 2025) (b)(3) |
| I10 | Allowed-amount files reachable | Consistency | Same, for allowed-amount links. | The required out-of-network file is effectively missing. | 45 CFR §147.212 (Oct 2025) (b)(3) |
| I11 | State match | Consistency | Linked files whose top provider practice state equals the plans' state (HIOS state code, else C1 state) ÷ linked files. Provider states from the CMS Doctors and Clinicians file (Oct 2026), NPPES only where it has no record. | Catches plans pointing to another state's network (Ambetter KS → a Kentucky network). NPPES addresses are often stale, so a fresher independent source comes first; a state over thousands of providers is robust. | Quality |
| I12 | Plan ID consistency | Consistency | Plan IDs that always carry the same type, market and issuer ÷ plan IDs. | A plan must be identifiable. | Quality |
| I13 | Duplicate plan rows | Usability | 1 − exact duplicate plan rows ÷ rows. | Duplicates inflate plan counts. | Quality |
| I14 | Unambiguous plan-to-file mapping | Usability | Plans listed in only one reporting structure ÷ plans. | Otherwise it is unclear which rate file applies. | Quality |
| I15 | Secure links | Usability | HTTPS file locations ÷ locations. | Plain HTTP downloads can be intercepted or altered. | Quality |

## 7. Limits

- Thirteen checks are at or above 0.99 for every reachable Centene file, nine at exactly 1.0: the files meet the enforced schema, so compliance separates them little. The checks still matter for other payers.
- M15 fences are relative to each file's own spread of rate ÷ Medicare: it measures consistency, not level; Medicare amounts use state-average GPCIs, not localities.
- I11 uses Medicare-enrolled clinicians first (76% of NPIs in the KS file); organization NPIs rely on NPPES.
- I7 accepts 5-digit issuer IDs because we cannot tell whether a 14-character plan ID was available.
- Weights and the dataset exponents are judgements, stated and fixed in `LOGIC.md` (R3.5, R3.11, R3.14).
